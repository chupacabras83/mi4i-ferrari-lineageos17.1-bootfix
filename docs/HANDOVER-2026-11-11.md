## 1. HTC Desire 12+ (`brepdugl`) — COMPLETE

**Goal achieved:** the phone boots Android 11 and stays up. No more factory-reset loop.

### Root cause (confirmed)
Android 11 `vold` could not build the FBE user-storage tree on this device's **stock Android 8.0 boot image**.
`fscrypt_prepare_user_storage` (CE) failed at `mkdir /data/vendor_ce/0` because `/data/vendor_ce` never
existed → `PackageManager: Destroying user 0` → `--prompt_and_wipe_data` → factory reset loop.
(`RescueParty`, the livedisplay "updatable-process" crash, and the Bluetooth crash were all **ruled out**.)

### Working fix (band-aid — /data is UNENCRYPTED)
Keep `/data` unencrypted with the original direct `on fs` mount, and pre-create the two missing dirs:

```sh
# in TWRP:
mount -t ext4 -o rw /dev/block/bootdevice/by-name/vendor /vendor
# restore original /vendor/etc/fstab.qcom  (/data unencrypted, by-name userdata, 'wait' only)
# restore original /vendor/etc/init/hw/init.target.rc  (with the direct 'on fs' mount)
mke2fs -t ext4 /dev/block/mmcblk0p53
mount -t ext4 /dev/block/mmcblk0p53 /data
mkdir -p /data/vendor_ce /data/media/0
chown system:system /data/vendor_ce
chown -R media_rw:media_rw /data/media
chmod 0770 /data/vendor_ce /data/media /data/media/0
# reboot
```

### What did NOT work (documented)
- **FBE** `fileencryption=aes-256-xts` → boot hang (Android 8 init fscrypt + Android 11 vold don't cooperate).
- **FDE** `forceencrypt=footer` (with 16 KB footer reserved: `mke2fs -t ext4 -b 4096 /dev/block/mmcblk0p53 6126325`) →
  encryption succeeded (`ro.crypto.state=encrypted`) but still reset (more dirs missing).

### Key HTC facts
- **Actual GSI is `bgS` (A/B), NOT `agS` (A-only)** as the old handover claimed — `ro.lineage.version=18.1-...-arm64_bgS`.
  This variant mismatch is a likely contributor; the correct A-only `agS` image is on disk at
  `C:\Users\iMac2019\brepdugl\lineage-18.1-arm64_agS.img` (not yet flashed).
- Partitions: system=mmcblk0p24, vendor=mmcblk0p25, boot=mmcblk0p21, userdata=mmcblk0p53, bootdevice=/dev/block/platform/soc/7824900.sdhci.
- adb/fastboot (32-bit) at `C:\Users\iMac2019\AppData\Local\Android\Sdk\platform-tools\`; x64 at `C:\Users\iMac2019\brepdugl\platform-tools-x64\platform-tools\`.
- Python (with OpenSSL) `C:\Python315\python.exe` — use it for HTTPS downloads (shell Schannel is broken).
- Device catch trick (recovery screen has USB off): tap "Try again" → `adb_race2.py` (background) catches the brief

## 2. Xiaomi Mi 4i (`ferrari`) — mostly done; WiFi remaining

### Done & verified
1. **Boot** — reaches Google setup screen, `sys.boot_completed=1`, no factory reset. (Fix chain: VINTF
   manifest.xml fixes + audio-policy fix below.)
2. **Audio** — `audioserver` SIGSEGV fixed. Root cause: `audio_policy_configuration.xml` was missing its
   `<volumes>` section → empty volume groups → null deref in `EngineBase::loadAudioPolicyEngineConfig()`.
   Fix: complete `<volumes>` (all 13 streams, inline `<point>`), tagNames in attachedDevices,
   concrete device types (`AUDIO_DEVICE_OUT_BLUETOOTH_SCO/A2DP`, not `*_ALL_*`).
3. **Bluetooth** — "Bluetooth keeps stopping" fixed. Root cause: `init.qcom.rc` had
   `seclabel u:r:bluetooth_loader:s0` for the `hciattach` service, but `bluetooth_loader` is **not defined**
   in the GSI's sepolicy → `setexeccon` EINVAL → HCI never up. Fix: removed that `seclabel` line.

### WiFi — IN PROGRESS (the remaining task)

**Symptoms:** `wifi_on=1` but `dumpsys wifi` = "Wi-Fi is disabled", flipping
`StaEnabledState → StaDisabledWithScanState` (enable fails). wlan0 interface + driver load fine
(`wlan.driver.status=ok`).

**Root cause found (two layers):**
1. *(fixed)* The WiFi HAL `libwifi-hal.so` hardcodes its control socket at
   `/dev/socket/wifihal/wifihal_ctrlsock`, but **no init script created the `/dev/socket/wifihal/` directory**
   → `ctrl_iface bind(PF_UNIX) failed: No such file or directory`. Fix applied (committed on-device):
   appended to `/vendor/etc/init/android.hardware.wifi@1.0-service.legacy.rc`:
   ```
   on post-fs
       mkdir /dev/socket/wifihal 0770 wifi wifi
   ```
2. *(remaining)* After the socket dir exists, the HAL still fails:
   `E WifiHAL: acquire_driver_supported_features: requestResponse Error:-3` →
   `Failed to get wifi Capabilities, error: -3`.
   This is a **HAL↔driver incompatibility**: the LineageOS 17.1 ferrari build's generic legacy
   `libwifi-hal.so` can't talk to the Qualcomm prima/WCNSS driver (WDI requests return -3).

### WiFi plan (next agent)
Swap in the **stock** prima-compatible `libwifi-hal.so`:

1. **Download the stock MIUI firmware** (in progress, see §3).
2. Extract `libwifi-hal.so` from the stock `system.img`.
3. Push to `/system/vendor/lib64/libwifi-hal.so` (back up the current one first), `chmod 0644`,
   `chcon u:object_r:vendor_file:s0` (or match the existing file's context), reboot, test.
4. If the stock Android 5 HAL doesn't work on Android 10, fall back to **PixysOS v2.4 (Android 9)**
   (the old handoff said it "flashed fine" — WiFi very likely works there).

The current on-device WiFi service is `vendor.wifi_hal_legacy` =
`/vendor/bin/hw/android.hardware.wifi@1.0-service.legacy` (class `hal`, user `wifi`, group `wifi gps`),
which loads `/system/vendor/lib64/libwifi-hal.so`.
